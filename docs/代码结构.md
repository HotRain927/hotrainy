## 三、几处"只应该有一份"的公共逻辑

重构时特意收敛到这里，**以后不要在各面板里各写一份**：

| 逻辑 | 唯一位置 | 说明 |
|---|---|---|
| 面板底色/边框/圆角 | `glass.cpp` → `Surface::buildFlatPanel(opacity, radius, dark)` | 不铺色底（纯透明）+ 三层错位的极细立体边框 |

| 配置读写 | `shared/config.cpp` | 只有一个 JSON 文件：`%APPDATA%\hotrainy\config.json` |

## 四、构建方式

源文件**按模块目录自动收集**，新增文件不需要改 CMake：

```cmake
file(GLOB HR_SOURCES "${CMAKE_SOURCE_DIR}/src/*.cpp")
foreach(mod app tagbar island settings search text audio glass shared)
    file(GLOB _HR_MOD "${CMAKE_SOURCE_DIR}/src/${mod}/*.cpp")
    list(APPEND HR_SOURCES ${_HR_MOD})
endforeach()
```

> ⚠️ 没有用 `GLOB_RECURSE`：否则会把 `src/tb/**`（注入侧，单独一套 target）重复收进主程序。

```bat
cmake -G Ninja -DCMAKE_BUILD_TYPE=Release -B build
ninja -C build -j4
```

**改了头文件一定要完整重建**（`ninja -C build -t clean` 后再 build）：本项目曾因陈旧 obj 布局出现两次真实崩溃。

## 六、加/改模块的标准动作

1. **加新模块**：`src/<模块>/xxx.cpp` + `include/hr/xxx.h` → 直接构建（CMake 自动收集）→ 需要跨模块协作时，回调定义放在模块自己的头文件里，由 `app/main.cpp` 接线。
2. **改现有模块**：只动该模块目录内的文件；若需要访问别的模块，通过 `app/main.cpp` 里已有的 hook 机制，不要在模块之间直接互相调用。
3. **加设置项**：`settings.cpp` 加一行（`toggle/segmented/slider/button`）+ `config.h`/`config.cpp` 加字段与读写 + `app/main.cpp` 的 `applySetting()` 加生效分支。

## 七、`main.cpp` 瘦身方案（待执行）

**做法**：每个 `wireXxx()` 接收它需要的模块引用（例如 `void tagbarWire(BarWindow& bar, HoverPanel& panel, Config& cfg)`），

**约束**：一次搬一个模块 → 立刻编译验证 → 提交。任何一步失败都可用 git 回退（当前 11 个提交）。

### 批量搬迁的**两个确切卡点**（已实测复现两次，均自动回滚，未污染仓库）

1. **`include/hr/shared/menu.h` 有 include 前置依赖**
   - 现象：把它 include 进新生成的 `*_wire.cpp` 后，报 `menu.h(51): C4430 缺少类型说明符` / `C2143 缺少","`
   - 原因：`menu.h` 依赖调用方**先**包含某些头（如 `windows.h` 之外的自定义类型/`std::function` 相关头）
   - 修法：在 `menu.h` 顶部补齐它自身的依赖（`#include <windows.h>` / `<functional>` / 需要的前置类型），让它**自包含**（这也是好习惯：头文件应当自包含）

2. **`makeHooks()` 未生成正确声明**
   - 定义：`main.cpp:937  ContextMenuHooks makeHooks() {`
   - 现象：生成的包装声明丢了返回类型 → `app_context.h(52): C4430 缺少类型说明符 … makeHooksWire`
   - 原因：`ContextMenuHooks` 是 `menu.h` 里的自定义类型，生成器解析 main.cpp 时把它当成了"未知类型"（且 `menu.h` 当时也没能编译通过，类型更解析不出来）
   - 修法：先解决卡点 1（让 `menu.h` 自包含），再重跑搬迁器即可；或手工为 `makeHooks` 写一个包装
