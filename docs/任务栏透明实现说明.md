# 任务栏透明实现说明

## 一、效果

任务栏背景完全透明，透出桌面壁纸，**图标保持清晰锐利**。

```
开启前                          开启后
┌──────────────────────────┐    ┌──────────────────────────┐
│ 桌面壁纸                   │    │ 桌面壁纸                   │
├──────────────────────────┤    ├──────────────────────────┤
│ ▓▓▓ 深色不透明底 ▓▓▓ 图标  │ →  │ （壁纸直接延续）      图标  │
└──────────────────────────┘    └──────────────────────────┘
```

## 二、为什么不能用常规办法

Win11（build 22000 以后）的任务栏不再是一个普通的 GDI 窗口。它的外观由
`Windows.UI.Composition` 渲染，承载在一个子窗口
`Windows.UI.Composition.DesktopWindowContentBridge` 上，
**背景与图标共用同一张 Composition 表面**。

下列手段在本机（Win11 26200.9711）逐一实测，**全部无效**：

| 手段 | 结果 |
|---|---|
| DWM 窗口属性 `DWMWA_*` 1–50 号 | 背景亮度恒为 45.4，无任何变化 |
| `DWMWA_SYSTEMBACKDROP_TYPE` = 1/2/3/4 | 无变化 |
| `DwmEnableBlurBehindWindow` | 无变化 |
| `SetWindowCompositionAttribute` 六种 AccentState | 最大变化 Δ=8.3，可忽略 |
| `DwmExtendFrameIntoClientArea` | 无变化 |
| 颜色键（colorkey） | 无变化 |
| `WS_EX_LAYERED` + `LWA_ALPHA` | 唯一有效，但作用在**整窗**——图标一起变淡 |
| 把 bridge 子窗口隐藏 | 整个任务栏变黑（连图标都没了），证明它是唯一渲染面 |

**根本原因**：那层挡住壁纸的暗底，是 explorer 进程**自己用 XAML 画上去的**。
从外面无论怎么改合成参数都改不到它。

## 三、实际采用的方案

进入 explorer 进程，找到那层背景元素，把它隐藏掉。

### 3.1 关键发现：任务栏的 XAML 结构

```
DesktopWindowXamlSource
  └─ RootGrid
       └─ Taskbar.TaskbarFrame
            ├─ Rectangle  Name="BackgroundFill"     ← 挡住壁纸的暗底
            └─ Rectangle  Name="BackgroundStroke"   ← 顶端那条浅色细线
```

**两个都要处理**：

- `BackgroundFill` 是背景板。只隐藏它会留一条边线。
- `BackgroundStroke` 是边框线。它就是任务栏顶端那道浅色细线，
  与背景板同级、是独立元素。

只处理 `BackgroundFill` 时，效果是"背景透明了，但顶上还剩一道边"。
两个都隐藏才是干净的完全透明。

图标是这棵树里**其它兄弟节点**。把这两个矩形整层隐藏，
背景消失而图标完全不受影响 —— 这就是"背景全透、图标清晰"能成立的原理。

**时序注意**：`BackgroundStroke` 可能比 `BackgroundFill` 晚一两个
树变更事件才出现。所以找到背景时排一次应用，找到边框时再排一次
（应用是幂等的，重复执行无害）。

### 3.2 用什么接口访问这棵树

Windows 自带一套 **XAML 诊断（XAML Diagnostics）** 机制，头文件
`xamlOM.h` 随 Windows SDK 提供，API 是公开的：

```
InitializeXamlDiagnosticsEx(连接名, 进程PID, nullptr, TAP_DLL路径, CLSID, nullptr)
```

系统会加载指定 DLL，回调它的 `DllGetClassObject(CLSID)`，
取出一个 `IObjectWithSite`，再调用 `SetSite(IXamlDiagnostics*)`
把诊断接口交给它。之后就能：

- `IVisualTreeService3::AdviseVisualTreeChange(callback)` 监听树变更
- 元素出现时按类型名与 Name 属性匹配
- `IXamlDiagnostics::GetHandleFromIInspectable` 把对象换成诊断句柄
- `IVisualTreeService2::GetPropertyIndex` + `IVisualTreeService::SetProperty` 改属性

### 3.3 怎么把 DLL 送进 explorer

用 `SetWindowsHookEx(WH_CALLWNDPROC, 钩子过程, DLL, explorer线程ID)`。
系统为了投递钩子会把 DLL 映射进 explorer 并调用它的 `DllMain`。

**这里有两个必须做对的点**：

1. **钩子过程必须由目标 DLL 导出**（我们导出了 `GlassBoot_HookProc`）。
   如果钩子过程写在主程序 EXE 里，Windows 无法把它投递到 explorer，
   只会把 DLL 短暂映射一下就卸载 —— 引导线程来不及运行，什么都发生不了。

2. **钩子必须一直持有**。释放钩子会让系统卸载 DLL，诊断通道和
   TAPSite 一起失效，任务栏立刻恢复原样。
   所以 **钩子的生命周期 = 透明效果的生命周期**。

## 四、踩过的坑（都是实测结论）

### 4.1 `InitializeXamlDiagnosticsEx` 要求进程 COM 状态"干净"

这是整件事最大的门槛。实测对照：

| 调用环境 | 结果 |
|---|---|
| 线程完全没做过 COM/WinRT 初始化 | **`0x00000000` 成功** |
| 线程先调过 `CoInitializeEx(STA)` | `0x80070490` 失败 |
| 进程里别的线程做过 MTA，再从新线程调用 | `0x80070490` 失败 |

`0x80070490` = `ERROR_NOT_FOUND`，非常难猜。

**而 C++/WinRT 在 DLL 加载时会跑静态初始化，其中包含 WinRT 套间初始化。**
所以只要 DLL 链接了 C++/WinRT，这个调用就永远失败。

对照实验：

```
纯 C 写的 DLL，同参数同线程     -> 0x00000000  成功
用 C++/WinRT 的 DLL            -> 0x80070490  失败
```

**这直接决定了架构必须拆成两层。**

### 4.2 不能在 `DllMain` 里直接调用

在 `DllMain` 里同步调用会返回 S_OK，但 explorer 紧接着以
`0xc0000409`（`__fastfail`）崩溃 —— 那里持有 loader lock。
`__fastfail` 会绕过 `SetUnhandledExceptionFilter`，所以崩溃时连日志都没有。

正确位置是**引导线程**：`DllMain` 已经返回，loader lock 已释放，
而该线程仍未碰过任何 COM/WinRT 状态。

### 4.3 `implements<>` 要把继承链上的接口都列出来

`IVisualTreeServiceCallback2` 继承自 `IVisualTreeServiceCallback`。
只写派生接口时，`QueryInterface` 到基接口会返回 `0x80004002`。

C++/WinRT 的 `implements<>` **只为显式列出的接口生成 QI 分支**，
不会因为 MIDL 的继承关系自动暴露基接口。

```cpp
// 错误：QI 到 IVisualTreeServiceCallback 失败
: winrt::implements<T, IVisualTreeServiceCallback2>

// 正确
: winrt::implements<T, IVisualTreeServiceCallback, IVisualTreeServiceCallback2>
```

### 4.4 `Shape.Fill` 写不进去，改用 `Opacity`

想换掉背景画刷，试了四种写法，**全部返回 `0x80004005` (E_FAIL)**：

```
element.Fill(透明画刷)                              -> E_FAIL
SetProperty(bg, 自造画刷句柄, Fill索引)              -> E_FAIL
SetProperty(bg, CreateInstance 造的句柄, Fill索引)   -> E_FAIL
ClearProperty(bg, Fill索引)                         -> E_FAIL
```

而**同一个索引 `GetProperty` 是成功的**（能读到当前画刷），
说明索引没错，是 XAML 诊断的写路径不接受对 `Shape.Fill` 这类依赖属性的写入。

**可行的替代**：把背景元素的 `Opacity` 设为 0。
`Opacity` 是普通依赖属性，可以正常写入：

```
GetPropertyIndex("Windows.UI.Xaml.UIElement.Opacity") -> idx=453
CreateInstance("Windows.Foundation.Double", "0")      -> handle
SetProperty(bg, handle, 453)                          -> S_OK      ✓
```

两个细节：
- 属性名必须写全（`Windows.UI.Xaml.UIElement.Opacity`），
  裸写 `"Opacity"` 返回 `0x80070057` (E_INVALIDARG)
- 值对象必须由 `CreateInstance` 创建，自己 new 一个 WinRT 对象
  再取句柄是不行的，系统只认自己创建的句柄

### 4.5 改动必须在回调栈之外

在 `OnVisualTreeChange` 回调内部直接改属性会被 XAML 拒绝。
做法是往消息队列投递一条自定义消息，等回调栈退回消息循环后再改。

## 五、代码结构

```
include/hr/tb/xaml/
  interfaces.h    COM 接口、CLSID、GlassBrush 枚举（跨进程契约）
  injector.h      注入器接口（主程序侧）
  tapsite.h       TAPSite 声明（DLL 侧）
  visualtree.h    视觉树监听接口（DLL 内部）
  taplog.h        DLL 侧独立日志
  crashguard.h    进程内崩溃捕获（诊断用）

src/tb/xaml/
  glassboot.c     ★ 纯 C 引导层 → GlassBoot.dll
  GlassBoot.def     导出 DllGetClassObject / GlassBoot_HookProc / GlassBoot_Shutdown
  crashguard.c    崩溃时记录调用栈（不依赖调试器）
  tapsite.cpp     TAPSite + COM 服务实现 → GlassTAP.dll
  visualtree.cpp  视觉树监听、定位 BackgroundFill、应用 Opacity
  taplog.cpp      DLL 侧日志（写 %LOCALAPPDATA%\hotrainy\tap.log）
  injector.cpp    注入器（主程序侧）
  GlassTAP.def      导出 DllGetClassObject

src/taskbar.cpp   主程序的服务层（开关、状态、兼容性检测）
include/hr/taskbar.h
```

### 两个 DLL 为什么必须分开

| 模块 | 语言 | 职责 |
|---|---|---|
| **GlassBoot.dll** | **纯 C**，不链接 C++ 运行时 | 抢在所有 C++ 代码之前建立 XAML 诊断通道 |
| **GlassTAP.dll** | C++/WinRT | 视觉树操作、COM 服务 |

`GlassBoot.dll` 建立通道后，系统回调它的 `DllGetClassObject`，
它再转发给 `GlassTAP.dll`。此时 C++/WinRT 的静态初始化不再有害
（通道已经建好了）。

引导层刻意保持极简：不创建线程等待、不遍历 PEB、
不在 `DllMain` 里做文件 I/O —— 每一个多余操作都可能破坏前置条件。

## 六、运行流程

```
hotrainy.exe
 │
 ├─ TaskbarService::SetTransparent(true)
 │   └─ tb::xaml::applyTransparent()
 │       └─ tb::xaml::injectIntoExplorer()
 │           ├─ LoadLibrary(GlassBoot.dll)          拿到模块句柄
 │           ├─ GetProcAddress("GlassBoot_HookProc") 取 DLL 自己的钩子过程
 │           ├─ SetWindowsHookEx(..., explorer线程)   系统把 DLL 映射进 explorer
 │           └─ 循环喂消息直到就绪事件被置位
 │
 ├─ explorer 进程内：
 │   GlassBoot.dll DllMain
 │    ├─ 确认自己是 explorer.exe
 │    ├─ LoadLibrary(Windows.UI.Xaml.dll)
 │    ├─ GetProcAddress("InitializeXamlDiagnosticsEx")
 │    └─ 在该线程同步调用 → S_OK          ← 建立诊断通道
 │
 │   系统回调 GlassBoot!DllGetClassObject(CLSID_GlassTAPSite)
 │    └─ 转发给 GlassTAP!DllGetClassObject
 │        └─ 返回 TAPSite 类工厂
 │
 │   系统调用 TAPSite::SetSite(IXamlDiagnostics*)
 │    └─ attachDiagnostics()
 │        ├─ QI IVisualTreeService3
 │        └─ AdviseVisualTreeChange(回调)     ← 开始监听树变更
 │
 │   OnVisualTreeChange 收到 Add 事件
 │    ├─ 匹配 Taskbar.TaskbarFrame → 关联 DesktopWindowXamlSource，取 HWND
 │    ├─ 匹配 Rectangle Name="BackgroundFill" → 记录元素
 │    └─ 投递自定义消息（等回调栈退出）
 │
 │   消息处理
 │    ├─ GetHandleFromIInspectable(背景元素) → InstanceHandle
 │    ├─ GetPropertyIndex("Windows.UI.Xaml.UIElement.Opacity") → 453
 │    ├─ CreateInstance("Windows.Foundation.Double", "0") → 值句柄
 │    └─ SetProperty(背景句柄, 值句柄, 453) → S_OK
 │
 └─ 任务栏背景消失，壁纸透出，图标不受影响
```

关闭时 `TaskbarService::Stop()` → `tb::xaml::shutdown()`：
先通过服务接口把 `Opacity` 写回 1，再释放接口，最后卸钩子。

## 七、兼容性与边界

**支持**：Windows 11 各版本（依赖的 `xamlOM.h` API 在 Win10 1809+ 就有）。

**已知冲突**：以下工具同样接管任务栏外观，同时运行会互相覆盖。
程序启动时会检测并提示：

- TranslucentTB
- RoundedTB
- ExplorerPatcher
- StartAllBack

**explorer 重启**：注入的 DLL 会随 explorer 一起消失，透明效果失效。
`TaskbarService::Refresh()` 可以重新注入（需要监听 `TaskbarCreated` 消息触发）。

**失败时的行为**：注入或设置失败**不会**留下副作用 ——
改动的是 XAML 元素的 `Opacity`，没有动系统设置、没有写注册表。
explorer 崩溃重启后一切自动恢复。
