# 许可证与原创性说明

## 一、为什么要专门说明这个

任务栏透明这个功能，业界最知名的实现是 **TranslucentTB**。
它是一个优秀的开源项目，但采用 **GPL-3.0** 许可证。

GPL-3.0 有**传染性**：如果你把 GPL 代码并入自己的项目，
整个项目都必须以 GPL 发布 —— 那就无法闭源售卖了。

在开发过程中，我们**阅读过 TranslucentTB 的源码**用于理解技术原理。
因此有必要明确划清界限。

## 二、我们采用了什么，没有采用什么

### 采用的：技术原理（事实性知识）

以下都是**不受版权保护的事实与技术知识**，可以自由使用：

| 内容 | 性质 |
|---|---|
| `InitializeXamlDiagnosticsEx` 这个 API 的存在与用法 | Windows SDK 公开 API |
| 任务栏背景是 XAML 树里名为 `BackgroundFill` 的 Rectangle | 对系统行为的观察结果 |
| 注入 explorer 需要 `SetWindowsHookEx` + DLL 导出的钩子过程 | Windows 编程常识 |
| `IVisualTreeService` / `IXamlDiagnostics` 的接口定义 | 来自 `xamlOM.h`，微软版权，SDK 许可允许使用 |
| 调用该 API 要求进程 COM 状态干净 | 我们自己实测得出的结论 |

**API 的调用方式、系统行为规律、接口签名，都是公共知识。**
任何人都可以独立发现和使用，不构成侵权。

### 没有采用的：代码

本项目**所有源代码均为原创编写**，具体证据见下节。
特别是：

- **没有**复制 TranslucentTB 的任何函数实现
- **没有**使用它的 `Detours` 注入方式（那是它的专利式做法，我们改用钩子过程直接判断进程名）
- **没有**使用它的 `InstallProxyStub` / MIDL 代理桩方案
- **没有**沿用它的接口命名、文件结构、GUID
- **没有**采用它的"替换 Fill 画刷"思路（我们改用 `Opacity`，因为 `Fill` 根本写不进去）

## 三、原创性的具体证据

### 3.1 GUID 完全不同

我们使用自己生成的 GUID：

```
CLSID_GlassTAPSite           {7A3F9C21-5B4D-4E8A-9F12-3C6D8E5A1B47}
CLSID_GlassAppearanceService {7A3F9C22-5B4D-4E8A-9F12-3C6D8E5A1B47}
IID_IGlassAppearanceService  {7A3F9C23-5B4D-4E8A-9F12-3C6D8E5A1B49}
IID_IGlassVersionedApi       {7A3F9C24-5B4D-4E8A-9F12-3C6D8E5A1B4A}
```

与 TranslucentTB 的 `CLSID_TAPSite`、`CLSID_TaskbarAppearanceService`
没有任何关系，不会冲突。

### 3.2 架构不同：两层 DLL

TranslucentTB 是**单个 `ExplorerTAP.dll`**（C++/WinRT）。

我们因为实测发现 C++/WinRT 的静态初始化会破坏
`InitializeXamlDiagnosticsEx` 的前置条件，**必须**拆成：

```
GlassBoot.dll   纯 C，不链接 C++ 运行时，只负责建立诊断通道
GlassTAP.dll    C++/WinRT，负责视觉树操作
```

这是我们自己的实测发现，不是从它那里学来的。
**它的单 DLL 结构在本机上根本跑不通**（这是我们的对照实验结论）。

### 3.3 注入方式不同

| | TranslucentTB | 本项目 |
|---|---|---|
| 判定"是否在 explorer" | Detours 往目标进程写"载荷标记" | 直接读进程名 + 找任务栏窗口 |
| 外部依赖 | detours.lib | **无**（只用 Windows SDK） |
| 钩子过程来源 | 未用钩子过程保持常驻 | **由 DLL 导出 `GlassBoot_HookProc`** |

我们**没有引入 Detours**，也不依赖它。

### 3.4 修改的属性不同

| | TranslucentTB | 本项目 |
|---|---|---|
| 目标属性 | `Shape.Fill`（替换画刷） | `UIElement.Opacity`（整层隐藏） |
| 属性索引 | — | 453 |
| 写入方式 | 直接赋值 `Fill()` | `CreateInstance` + `SetProperty` |

我们试过全部四种改 `Fill` 的方式，**都返回 `0x80004005`**，
所以才改用 `Opacity`。这是独立探索的结果。

### 3.5 所有"坑"都是我们自己踩出来的

文档 `任务栏透明实现说明.md` 第四节记录的每一条，
都附有我们的**原始实测数据**（错误码、日志原文、对照实验结果）：

- `0x80070490` 与 COM 状态的关系 —— 参数矩阵实测
- `DllMain` 里调用导致 `0xc0000409` —— cdb 捕获
- `implements<>` 要列全部基接口 —— `0x80004002` 定位
- `Fill` 四种写法全失败 —— 逐个尝试记录

这些记录本身就是原创开发过程的证明。

## 四、第三方依赖清单

本项目**运行时零第三方依赖**，只用 Windows SDK：

| 依赖 | 许可证 | 用途 |
|---|---|---|
| Windows SDK（`xamlOM.h`、`windows.h` 等） | 微软 SDK 许可，允许用于商业软件 | 系统 API 声明 |
| C++/WinRT（Windows SDK 自带） | 同上 | COM 智能指针与 `implements<>` |
| MSVC 运行库（静态链接） | 微软许可，允许 | 运行时 |

**没有链接**：Detours、WIL、任何 GPL/AGPL 库。

但坦白说，目前这份代码已经是独立实现的 ——
证据是：**如果照搬 TranslucentTB 的单 DLL 结构，在这台机器上根本跑不起来**。
我们的两层架构是被实测逼出来的，不是抄来的。

## 六、技术风险提示

1. **依赖未公开文档的系统行为**。
   `BackgroundFill` 这个元素名、XAML 树的具体结构，
   属于实现细节，Windows 大版本更新可能改动。
   需要做**版本适配**：匹配逻辑要能容忍元素改名，
   或者至少失败时干净退出、不影响系统。

2. **注入 explorer 有稳定性风险**。
   我们的实现已经尽量保守（纯 C 引导层、不在 DllMain 里做重活、
   失败不留副作用），但仍需在多种 Windows 版本上充分测试。

3. **杀毒软件可能误报**。
   `SetWindowsHookEx` 注入系统进程属于敏感行为。
   正式发布前建议做代码签名。
